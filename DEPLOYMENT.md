# Deployment

The app deploys as **two services**: a static frontend on Vercel and a Node API
with Postgres on Render.

## Why split, rather than one service serving both

The obvious alternative is to have Express serve the built frontend from
`dist/`, which is one service and no CORS. It was rejected for one reason: on
Render's free tier a service **sleeps after 15 minutes of inactivity**, and the
next request waits 30–50 seconds for it to wake. If that service also serves the
HTML, a visitor's *first paint* pays the cold start — they stare at nothing and
conclude the site is broken.

Splitting moves the cold start off the critical path. Vercel serves the frontend
from a CDN, so it is always warm: the landing page, login, and navigation paint
immediately. Only the first *lesson generation* wakes the API, and that action
already shows a progress state for ~10s of AI calls, so the extra wait lands
somewhere the user is already expecting to wait. `Dashboard.tsx` escalates its
progress copy with elapsed time and names the cold start explicitly once the
wait exceeds 25 seconds.

The costs of the split, accepted knowingly: an explicit CORS allowlist, and the
API origin has to be baked into the frontend bundle at build time.

## Backend → Render

1. **New > Blueprint**, point it at this repository. `render.yaml` creates the
   web service and a free Postgres instance.
2. Set the two secrets it prompts for:
   - `ANTHROPIC_API_KEY`
   - `CORS_ORIGIN` — leave blank for now; the Vercel URL doesn't exist yet.
   `JWT_SECRET` is generated by Render. `DATABASE_URL` is wired automatically.
3. The build runs `npm run migrate`, which applies `database/migrations/` in
   order and records them in `schema_migrations`. Applying the schema by hand is
   what caused the drift that broke lesson submission — don't do it.
4. Check `https://<service>.onrender.com/health`. It runs `SELECT 1`, so `"ok"`
   means the database is genuinely reachable.

## Frontend → Vercel

1. **Add New > Project**, same repository, **root directory `frontend`**.
   Vercel detects Vite; build `npm run build`, output `dist`.
2. Environment variable:
   `VITE_API_URL = https://<service>.onrender.com/api`
   Vite inlines `import.meta.env` **at build time**, so changing this requires a
   redeploy, not just a restart.
3. Deploy, then go back to Render and set `CORS_ORIGIN` to the Vercel URL
   (e.g. `https://lingua.vercel.app`). Render redeploys automatically.

### The rewrite rule in `frontend/vercel.json`

```json
{ "source": "/(.*)", "destination": "/index.html" }
```

This is not optional. The app uses `BrowserRouter`, so `/lessons/12` is a real
URL the user can refresh or link to — but no file exists at that path on disk.
Without the rewrite the CDN looks for `/lessons/12`, finds nothing, and returns
its own 404 before React ever loads. The rewrite serves `index.html` for every
path and lets the router resolve it client-side.

The paired `Cache-Control` headers exist because Vite fingerprints asset
filenames (`index-BgHfc0V7.js`). Those are immutable and cached for a year;
`index.html` is `no-cache`, so a deploy is picked up on the next load rather than
serving a stale page pointing at deleted assets.

## Environment variables

| Variable | Where | Notes |
|---|---|---|
| `DATABASE_URL` | Render | Wired from the database by `render.yaml` |
| `JWT_SECRET` | Render | Generated. Changing it signs out every user |
| `ANTHROPIC_API_KEY` | Render | Server-side only, never reaches the browser |
| `CORS_ORIGIN` | Render | Comma-separated Vercel origins |
| `NODE_ENV` | Render | `production` — enables Postgres TLS and trust-proxy |
| `VITE_API_URL` | Vercel | Baked in at build time |

## Known free-tier limits

- **The API sleeps after 15 minutes.** Mitigated as described above, not hidden.
- **Render's free Postgres is deleted after 30 days.** The schema is reproducible
  from migrations; user accounts and lessons are not. Upgrade before this matters.
- **`trust proxy` is set in production** so rate limiting sees the real client IP
  rather than Render's load balancer, which would otherwise make every
  IP-keyed limit one shared bucket.

## After deploying, verify

```bash
curl https://<service>.onrender.com/health      # {"status":"ok","database":"connected"}
```

Then in the browser: register → create a lesson → submit it. Check the Network
tab for requests going to the Render origin with no CORS errors, and hard-refresh
on `/lessons` to confirm the SPA rewrite works.
